# Schema self-review

## Quick answers to the six questions

1. **Coverage:** Every requirement with *Stores data? = Yes* has a table or column. Gon's tasks (join, see position and status) use `students`, `services` and `tickets`. Killua's tasks (view queue, call next, mark served) use `tickets.status`, `called_at` and `finished_at`. Every column is needed: `is_active` for FR-11, `called_at` for "at the window for 2 min" in my wireframe, and `finished_at` for the completed list (FR-12).
2. **One fact in one place:** The student's name was copied into every ticket in Week 3. Now it is stored once in `students`. (See entry 3.)
3. **Facts, not results:** I store no position, count or waiting time. Position, "waiting per service" and "served today" are all computed from `tickets`.
4. **Bad data:** A double tap, a wrong Student ID, a wrong status and a missing service are stopped by constraints, except one case. (See entries 1 and 2.)
5. **Deletes:** Both foreign keys use RESTRICT on purpose, so no delete can destroy the history staff need for FR-12.
6. **Types:** Every moment in time is `timestamptz`, `is_active` is a boolean, and the Student ID is text only because it contains a dash.

## Entry 1: One active ticket per student

**Works well:** `students.id_number` is `UNIQUE` with a `CHECK`, so the database never holds two rows for the same Student ID, and a typo like `123` is rejected. This follows FR-09.

**Problem:** Found with question 4 (bad data). The rule "a student can have only one ticket that is waiting or called" is only checked in my Python code. A double tap, or two browser tabs sending the form at the same moment, could still create two tickets, because the database would accept both.

**Change:** I made the rule a real database rule in `schema.md`: a partial unique index on `tickets(student_id)` that applies only to tickets with status `waiting` or `called`. Served and no-show tickets are not counted, so a student can join again later. It was optional before, and now it is part of the schema.

## Entry 2: Leaving the queue and not showing up are different

**Works well:** The `CHECK` on `tickets.status` allows only fixed values, so a typo like `"calld"` can never reach the database.

**Problem:** Found with question 4 (bad data) and question 1 (coverage). In Week 3, a student who leaves the queue (FR-07) and a student who does not show up when called (FR-06) both became `no-show`. Staff cannot tell them apart, and the later report about people who left before being served (a Should-level idea in my notes) would be wrong.

**Change:** I added a fifth status, `left`, to the `CHECK` in `schema.md` and to the ERD note. It is much cheaper to add now than after the table has data. In Part 5, the Leave button will set `left`, and Call and Serve stay the same.

## Entry 3: A student's name is typed on every visit

**Works well:** The name lives only in `students`, and each ticket holds just a `student_id`. If the registrar fixes a spelling, it changes in one row.

**Problem:** Found with question 2 (one fact in one place). My join form asks for the name every time, so a student can type a different spelling on a second visit. The database would then have one student with two possible names, and I have to decide which one wins.

**Change:** Rule added to `schema.md`: the Student ID identifies the student. When someone joins, the app looks up their Student ID. If it exists, the stored name is updated to the latest one typed. If not, a new student is created. The schema itself does not change.

## Entry 4: Ticket numbers keep growing

**Works well:** `tickets.id` is generated by the database, so two students can never get the same number (NFR-02). This is safer than my Week 3 code, which used the last ticket number plus one.

**Problem:** Found with question 1 (coverage). In a real office the numbers usually start again every morning, but `tickets.id` only goes up, so after a few weeks a ticket would read R-1042 instead of R-007.

**Change:** I kept the schema as it is. Resetting numbers every day would need an extra column (for the queue date) and a rule that makes the number unique per day. That is more than the minimum version needs, and the ticket number still does its job of being unique and in order.
